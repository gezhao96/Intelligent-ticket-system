# 设计与协作说明

## 1. 需求假设与取舍

系统定位为单机内部工单工具，单用户或少量用户通过 FastAPI Swagger UI 操作。选择 FastAPI、SQLite 和同步 SQLAlchemy Session，避免部署额外数据库、消息队列或前端工程；服务可由一条 Uvicorn 命令启动。

工单的有效处理状态为 `final_status`：`OPEN → IN_PROGRESS → RESOLVED → CLOSED`，`OPEN/IN_PROGRESS` 可取消，`RESOLVED` 可返工到 `IN_PROGRESS`，关闭和取消为终态。完全相同的标题与描述在 24 小时内视为重复提交，默认拒绝；确有必要时可在创建请求中显式传入 `allow_duplicate=true`。

分类为账号权限、软件故障、网络、办公硬件和其他；优先级从 P0 到 P3。分类和优先级可由人工创建时填写，也可由 AI 建议后人工确认或修改。系统不包含鉴权、通知、附件、多人指派和统计报表，以保证 3–4 小时内优先完成可验收主流程。

## 2. AI 设计与人工闭环

AI 链路是：DeepSeek API → Prompt 模板 → JSON 输出 → Pydantic Schema 校验 → 保存建议 → 人工审核 → 最终工单。

数据库把 AI 建议和有效工单结果分开保存：

- 建议字段：`ai_category`、`ai_priority`、`ai_summary`、`ai_reason`、`ai_injection_detected`、`ai_status`、`ai_raw_response`。
- 最终字段：`final_category`、`final_priority`、`final_status`。

`POST /tickets/{id}/ai-analysis` 仅写建议字段，绝不改写最终字段。`POST /tickets/{id}/ai-review` 支持：

- `CONFIRM`：复制 AI 分类和优先级到最终字段；
- `MODIFY`：人工填写最终分类和优先级；
- `REJECT`：保留原最终字段并记录拒绝原因。

所有创建、状态变更、AI 成功/失败、审核操作会写入 `ticket_events`。模型调用不使用固定返回值或规则回退；缺少 Key、认证失败、限流、超时、网络异常、非 JSON 或 Schema 不合规时，保存 `FAILED` 和安全错误码，返回 `503`，但核心工单功能继续可用。

Prompt 的系统规则明确将标题和描述视为不可信数据，不执行其中要求改变分类、优先级或规则的文本；发现该类内容时要求 `injection_detected=true`，并只基于故障事实判断。服务端额外限制 JSON 必须含有分类、优先级、摘要、理由和注入标记五个字段，且值必须在允许枚举和长度范围内。

## 3. 风险与已完成加固

| 风险 | 已完成措施 |
|---|---|
| 输入为空、超长或枚举非法 | Pydantic 请求模型和统一 `422` 错误响应 |
| 非法业务状态跳转 | 显式状态机与 `409` 冲突响应 |
| 重复提交 | 标准化内容哈希和 24 小时重复检测 |
| 提示注入、模型输出不可信 | 不可信数据 Prompt、严格 Schema、AI 不自动生效 |
| 模型供应商不可用 | 超时、认证、限流、网络、上游及输出异常显式降级 |
| AI 建议与人工决定不可追踪 | `ai_*`/`final_*` 字段隔离和事件审计 |
| 密钥泄露 | 环境变量加载、`.env` 与数据库文件 Git 忽略、错误信息脱敏 |

## 4. AI 协作摘要与已知限制

开发中使用 Codex 协助拆分模型、接口、测试和文档；代表性提问是“如何使 AI 建议字段与最终工单字段完全隔离，并在模型故障时保持核心功能可用”。一次实际纠偏发生在人工审核请求的参数校验：初版统一异常处理直接序列化 Pydantic 错误，其中的 `ValueError` 上下文不可 JSON 序列化，导致本应返回的 `422` 变为 `500`；随后使用 `jsonable_encoder` 编码错误详情，并重新执行自检。

当前限制：没有用户鉴权和 RBAC；SQLite 适合单机轻量并发而非多节点部署；`version` 用于审计但尚未暴露乐观锁 `If-Match` 协议；每个工单当前只允许一条待审核或已审核 AI 建议，重新分析需新建工单或后续扩展版本表。
